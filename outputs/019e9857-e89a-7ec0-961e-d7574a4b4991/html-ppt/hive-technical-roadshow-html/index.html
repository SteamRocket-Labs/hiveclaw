开场先把定位讲清楚：Hive 不是聊天机器人，也不是一个 LangGraph 旁边的 UI。我们真正做的是一套数字员工基础设施，让 agent 有长期身份、有可治理记忆、有 durable runtime，也有企业级权限和审计。

这一页右边四个数字来自今天的当前代码扫描，不是旧文档：版本 1.7.0、107 个工具注册点、158 个后端 service，以及 RLS 加审计这条企业边界。你可以先用这几个数字建立技术可信度。

过渡到下一页时说：为什么这件事需要平台？因为企业 agent 的问题不只是模型够不够聪明，而是运行过程没有生命体征。

这一页是问题重构。你可以先说：现在大家谈 agent，经常把重点放在模型是不是够强。但在企业场景里，模型强只是起点，真正的问题是agent 不能稳定地活在组织里。

第一，状态断裂。普通 chatbot 一关窗口就什么都没了，身份和偏好都不是资产。第二，执行脆弱，长任务跑一半页面刷新，或者后台失败，用户很难知道发生了什么。第三，治理缺席，外部消息、文件写入、公司边界这些风险都被塞进 prompt 里。

所以 Hive 的切入点不是“再包一层 chat UI”，而是把身份、执行、记忆、权限这些底层能力做成平台。

AI-native design law

释放模型能力，
把约束放在行动边界。

L1Unleash the model first

总结、规划、提取、综合、判断都给 LLM 完整输入和足够输出预算。

L2Harness constrains, never replaces

治理层限制 agent 能做什么，而不是削弱它怎么思考。

L3Neutral enterprise control plane

模型平等，组织权限、预算、审计和协作治理在平台层统一。

source: AGENTS.md / AI-Native Design Law

这页是我们的设计原则。你可以用一句话讲：Hive 不用治理层替代模型思考，而是把治理层放在行动边界上。

L1 是释放模型。凡是需要智能判断的步骤，比如总结、规划、提取、综合，都应该给模型完整上下文和足够输出空间，不要靠机械规则假装智能。L2 是 harness 的位置：权限、预算、审计、审批是包在外层的，它限制 agent 能做什么，不限制 agent 怎么想。

L3 是 Hive 的平台身份：我们不是某个模型供应商的附属品，而是组织侧的控制中台。换模型也可以，治理、记忆和执行语义保持一致。

这页是整体架构图。讲法上不要逐个念框，重点是同一条 runtime 路径。不管用户从 Web chat、飞书、定时任务、webhook 还是 Office 入口进来，最终都进入后端统一处理。

FastAPI 层负责 API、webhook 和管理面；中间是 invoker 加 AgentKernel，处理模型调用、多轮工具循环、LoopGuard、压缩和工具预算；再往右是 ToolRuntimeService，所有副作用都在这里进入治理链路。

最底下这条带子很重要：Memory Control Plane 和企业控制中台包住全路径。也就是说，Hive 的差异不是有多少工具，而是这些工具全都在同一套 owner/company、tenant、审计和审批语义下运行。

source: runtime/invoker.py · kernel/engine.py · tools/service.py

这一页可以讲得稍微技术一点。Hive 的核心不在某个 prompt，而在这个 invocation path。入口可以很多，但进入 runtime 之后是同一个 kernel。

invoker 先解析模型、租户、工具和动态记忆。AgentKernel 负责多轮 LLM 工具循环，包括 LoopGuard、mid-loop compaction、工具结果 eviction 和预算控制。关键点在 ToolRuntimeService：它是所有副作用的统一入口，文件写入、发消息、Office 操作、MCP 调用都不能绕过。

下方两块说明为什么这是企业平台。左边是记忆怎么被动态激活；右边是动作怎么过 preflight、checkpoint 和 audit。这个组合决定了 Hive 可以让 agent 真正工作，而不是只在聊天框里回答。

这里要避免把 Hive 讲成“我们也有 RAG”。Hive 的记忆更像资产层。左边是 Markdown memory pyramid，T0 是原始日志，T2 是抽取后的原子学习，T3 是 Heartbeat 策展后的语义记忆，最上面 soul.md 是身份。

但真正重要的是右边：存储只是路径，控制平面决定运行时行为。谁是 owner，当前用户和公司上下文是什么，哪些记忆可以写入，哪些敏感信息要剥离，为什么 agent 做出某个动作，都需要被治理。

你可以强调一点：Memory Control Plane 让 agent 能学习，但不会把凭据、隐私、公司边界冲突直接写进长期记忆。这个是企业版自进化 agent 的基本盘。

这一页是最近架构讨论里很重要的定稿。讲的时候先把边界说清楚：Plan Mode 和 Workflow 是并列底座，不是互相包含。

Plan Mode 负责确认边界：能不能开始、要不要人确认、确认的计划是什么。Workflow 负责执行控制流：开始之后怎么确定性推进、怎么暂停、怎么恢复、怎么审计。两者当然可以组合，比如高风险 workflow launch 被 plan gate 拦住，但概念上不能混在一起。

底部这条共享能力是关键：RuntimeTask、tenant boundary、budget envelope、audit、resume、checkpoint。这个设计让 workflow 能成为 Hive 的 runtime 基础能力，而不是某个 deep research 或 office 功能的附属实现。

这页可以更工程化一点。Workflow 的定义不是代码，而是结构化数据：sequence、bounded fanout、condition、gate、wait。安全不来自 JSON 本身，而来自 compile 和 admission。

编译阶段会做 schema、capability、风险分级和预算预检；运行阶段落到 RuntimeTask，步骤和叶子调用都有 journal。这样 crash 之后可以 resume，而且不是整步重跑，而是 leaf-level replay。

下面四个 guard 是现场需要讲清楚的边界：没有任意代码执行；不可逆动作必须 gate；resume 是按 input_hash 和 definition_hash 复用；Deep Research 新 workflow 路径还应按 gated rollout 表达，不要讲成默认生产打开。

这页是企业客户或投资人最关心的 trust story。你可以直接说：Hive 的治理不是在 prompt 里写“请你小心点”，而是在工具执行、数据库会话和审计对象上做 fail-closed。

中间这个 ToolRuntimeService.execute 是所有副作用的单入口。周围六个边界分别是 tenant/RLS、capability policy、action preflight、checkpoint、audit decision trace、secrets boundary。

讲的时候可以举例：如果 agent 要发外部消息、读敏感资源、执行不可逆动作，它不是靠模型自己判断，而是会被 preflight 和 capability gate 拦住，必要时生成 checkpoint 等人确认。这就是 Hive 和普通 agent 框架的区别。

这一页要讲得诚实。Deep Research 是 Hive 复杂 agent 工作的压力测试，因为它同时需要 planner、worker fanout、source ledger、synthesis、critic 和 artifact composer。

左边是当前可见能力：deep_research 工具、spawn_subagent、Work Ledger events 和 source/artifact contract。中间是我们已经识别出来的风险，比如 worker context 污染、final writer 像拼接、busy-poll、duplicated export。

右边是合流路线：把旧 Deep Research 执行链迁到 Leaf Preset Registry 和 workflow runtime，叶子执行过 governed subagent，journal 和 artifact refs 统一。最后一句提醒很重要：现场可以讲这是高价值试点和架构方向，但不要说 gated path 已经默认生产打开。
