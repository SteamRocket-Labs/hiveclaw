## 1. 我们要做成什么

### 1.1 一句话和三个面

团队里每个人都能用的 Claude Code 级助手。主路径只有一条：**对话 → 干活 → 拿结果**。

| 面 | 对谁 | 要做到 | 学谁 |
|---|---|---|---|
| 能力 | 每个人 | 读写文件、跑代码、查资料、出成果、接着改；计划、目标、技能、子 agent、压缩和续跑都在 | Claude Code（能力和生命周期的语义底座，06-24 北极星） |
| 体验 | 成员 | 点开 bot 就在对话里；事情交出去，结果回到原处；用到的那一刻才问；顺利时只说结果，卡住时说清卡在哪 | Grok Bot 的封装（11-04 拆解） |
| 管理 | 公司 | 数字员工归公司，只建不删；人走了交接；对外动作先批；凭据托管；花费有上限；做过什么查得到；能私有化 | 我们自己的风控和管理体系（06-05、06-25、07-20、09-05 的历次决定） |

### 1.2 和 Claude Code、Grok 比

| | Claude Code | Grok Bot（含团队版） | HiveClaw |
|---|---|---|---|
| 给谁用 | 一个工程师，在自己的电脑上 | 一个人，团队版加共享 bot | 一家公司的所有人 |
| 谁出钱、归谁 | 个人或公司买席位，会话在本机 | 个人或团队付费；bot 归建它的人，共享 bot 删了，全队在上面的对话和例程一起没了（`shared-bots.md:160-172`） | 公司出钱（模型 key、预算、连接都是公司的），数字员工和它的工作记录归公司 |
| bot 的寿命 | 没有 bot 的概念 | 建了可以删 | 只建不删：停用、恢复、交接 |
| 在哪里用 | 终端、IDE、桌面 | 网页、X Chat、Slack | 网页为主；飞书、钉钉、企微、Slack、Telegram |
| 管理 | 几乎没有 | 管理员页成员看不到；连接不能下发给成员（“Pushing connectors to members … is not available”）；文档里只有账户级花费上限，没有 bot 级的 | 管理员后台：成员和登录、数字员工、模型和预算、公司连接、审批规则、审计日志 |
| 部署 | 本机 | 只在它自己的云 | 云上和私有化 |

我们拿什么：Claude Code 的能力（全部保留，只是不摆在默认界面上）；Grok 的封装（一个会话管住所有在办的事，用到时就地问，按钮写明范围）。

我们不拿什么：
- Grok 的个人归属模型：bot 跟人走、删 bot 连带删数据；
- Grok 的共享电脑前提；
- Grok 由 bot 自己替每个任务选模型、用户和管理员都不能选的做法（私有化客户自带模型，模型要由管理员定）；
- 照抄表面。控件藏起来了，失败、审批、成果的反馈也跟着藏起来，这是 11-04 拆解里写过的第一种错。

### 1.3 定位措辞改一处（11-04 已定）

现行产品定义第 14 行写的是：“CC 级的能力，Grokbot 级的封装，企业敢用。治理是让企业敢用的底线，本身不是卖点。”

你 11-04 说：“我们和 Grok 的区别就在于我们有一套风控和管理体系。”

两句话并不完全冲突。11-03 要去掉的是循环加进用户等待路上的那些内部证明，比如每次读取都校验、处处对账、回执，而不是管理体系本身。我的提议是改成：

> **差异化：CC 级的能力，Grok 式的同事体验，公司的东西归公司、管得住。**管理体系是我们和 Grok 的区别，它放在管理员那一侧；成员只在对外或不可逆的那一刻碰到它。“每一步都证明一遍”的那类机制仍然冻结。

改了这一句，AGENTS.md 里“Governance is the floor … it is not the product”也要跟着改。已按这句改了产品定义和 AGENTS.md（第 11 节第 5 项）。

## 2. 用户看到什么

### 2.1 成员

- **侧栏**：bot 列表（我的助理排第一）、新建数字员工、设置。没有别的。B3+B4 已做（`37d0e98a`）。
- **点开一个 bot**：进入它最近那段对话。页头有“历史”，里面是这个 bot 的其他对话和“新对话”。能管理这个 bot 的人，页头多一个“设置”。B5 已做（11-04）。

- **用到时就地问**：要密钥、要连接、要绑 IM、要审批、要回答问题时，对话里出一张卡。办完卡收成一行，原来那件事接着跑（A4 续接合同）。

- **状态只有五种**：运行中、等你决定、完成、失败、已停止（A3 已做）。
- **设置**：只放清单，每一项都能撤销。清单有这几张：账户、知识库、本地连接、保险箱、连接、“以后都允许”的规则、渠道、定时任务（D11）。

## 3. 归属和权限

### 3.1 原则

你 11-04 的原话：“人是用户，所谓的数字员工是可被创建、不可被删除的，相关资料也应该留在公司。我们遵循的一个原则是‘谁出钱资料留给谁’，或者说各自有一半的职责。”

已定（第 11 节第 1 项）。你 11-04 的回复：“我按照这个执行好了 或者说，在这个场景里面没有个人知识，实际上是没有的。因为这是公司给配的 bot，所以我个人觉得这件事大部分应该都算公司的吧”。
- **谁出钱资料留给谁。** 公司付模型、预算和连接的钱，所以数字员工、它做的事、它产出的成果、成员上传的知识，都归公司。没有“个人知识”这一类。
- **只有身份归个人。** 登录身份和个人凭据（自己账号的令牌、密码、保险箱里的个人条目）归个人。离职时吊销，不转给任何人，转出去就等于让别人冒用他的身份。用这些凭据拿进 bot 或知识库的资料归公司，留下。
- **各自一半的职责。** 责任分两半，不是所有权对半分。
  - 用的人对“让 bot 做什么”负责：他发起的事、他批的对外动作、他的会话权限档位。
  - 公司对“bot 能做什么”负责：能用的模型和连接、预算上限、审批规则，并且留存全部记录。

这和历次决定基本一致，有两处要改：
- 06-05 的资产模型：公司是组织，每个 bot 像组织下的仓库；连接类资产（模型、MCP、渠道）由公司集中持有。
- 06-25：“The permission incident came from mixing those layers”。会话里的权限档位是个人的方便，公司的规则是公司的，两层不能混。那次定的硬规则是“员工能建 bot，只有管理员能删”。**这一条现在要改成“谁都不能删，只能停用”。**
- 07-20：离职不是物理删除。bot 交给接手人，记录全部保留。那份合同还写了个人资源不随 bot 转移（合同 :94）。**知识这一部分按你 11-04 的回复改：成员上传的知识归公司，随交接交给接手人。**
- 09-05 PDEC-013：三种角色；管理员在自己的范围内有全部业务权限，包括员工 bot 的私有会话、文件和知识；凭据不明文展示。

### 3.2 三类东西

| 类别 | 包括 | 归谁 | 能不能删 | 人走了怎么办 |
|---|---|---|---|---|
| 公司资产 | 数字员工（身份、设定、记忆、技能、工作区文件）、成果、成员上传的知识、公司知识库、公司连接、模型 key、预算、审计 | 公司 | bot 本身不能删，只能停用和恢复。里面的内容（记忆条目、技能、文件、知识）照常可以改和删，按现有权限；成果的历史版本和审计保留 | 留在公司；bot 和他上传的知识交给接手人 |
| 和公司 bot 的工作记录 | 对话、交出去的事、审批记录、定时任务 | 公司留存；默认只有本人看得到，管理员在自己的范围内能看，看了留审计 | 本人只能从自己的列表里移除（隐藏），数据不删 | 记录留存；没做完的事和定时任务交给接手人确认 |
| 身份和凭据 | 登录身份、个人账号的授权（例如用自己的飞书账号授权）、自己账号的令牌和密码、保险箱里的个人条目 | 个人 | 本人可以删 | 吊销，不转给任何人；用它拿进来的资料留在公司。接手人要用同一个外部系统，用自己的账号重新授权 |

“个人数据默认私有”（治理底线 3）的意思是：其他成员看不到。它不挡公司管理员，PDEC-013 已经定过这一点。

离职人以前的对话：作为公司记录留存，管理员按 PDEC-013 能看并留审计；默认不给接手人看。接手人接的是 bot（连同记忆、知识、文件、成果、定时任务）和没做完的事，交接卡上带着每件事已知的结果，不需要翻旧对话。你要接手人也能看，说一声，G2 加一个只读入口。

### 3.4 两层权限，不能混

- **会话权限档位**（请求批准 / 替我批准 / 完全访问）：个人的方便，只管这次对话里要不要逐个问他。06-25 定的，保留。
- **公司规则**：租户隔离、资源权限、审批规则、预算、凭据。任何档位都绕不过。
- **bot 用谁的身份做事**：用发起人的。交给另一个 bot 也是用发起人的权限，用量也算在发起人头上（界面结论 §2、§5.5；D4 逐条验证）。定时任务按创建它的人的身份跑，这是 07-20 合同的设计：请求人不能被静态负责人替换（合同 :21，`trigger_resource_authority.py:266-278`）。人离职后，他建的定时任务被隔离，接手人确认后才继续（G2）。

### 3.6 我们的管理体系具体比 Grok 多什么

- bot 归公司，删不掉，人走了交得出去。Grok 删共享 bot 连带删全队的对话和例程。

## 5. 工程原则（已写进 AGENTS.md 和产品定义，这里只列要点）

- 每段代码只问两件事：它在不在“对话 → 干活 → 拿结果”这条路上？它是不是六条底线之一？
- 一轮开始时确认一次身份和权限，往下传。
- 只在对外可见或不可逆的动作那一刻检查。检查不通过，只拿掉那一件事。
- 内部状态不给用户看。
- 对外边界用真实渠道和真实安装验证。
- 新机制要 owner 批准。某一片净增行数，或审查发现新加了机制，就停下来回报。
- 先断开、后删除。冻结的东西从默认路径和默认界面断开，P3 再删。
- 控件数、净行数、测试数这类计数只是观察；“拿得出手”由黄金任务和五种状态判定。
- 任何拦下来的地方都要给出路：修复、重试、取消或放弃。停用要能恢复；离职时效果不明的事要能确认后继续。
- 以“安全”“合规”为名加的机制，要说清它挡的是哪种伤害、保护什么、为什么是最小的做法，并且主路径照样好用。

## 10. 风险

- **把“数字员工不删”做成“什么都不能删”。** 法律要求删除个人信息的情况（例如员工要求删除自己的个人数据）要有一条由管理员发起、留审计的路径，不能没有。这一条要你定，必要时咨询法务。我不对法律义务下结论。
- **管理员能看员工的私有会话（PDEC-013）。** 这是你 09-05 定的。对客户要在合同或产品说明里写清楚，否则成员会觉得被监视。界面上，成员的“历史”不显示这一点；管理员每次查看都留审计。
- **照抄 Grok 的表面。** 控件藏了，失败、审批、成果的反馈也跟着藏。验收只看黄金任务和五种状态。
- **一个会话同时办 15 件事，会撞上并发上限和重复消耗。** E6 实测时记下每件事的用量和并发报错；预算上限本来就是治理底线 6，先核对现有功能够不够，不另立工程。
- **A4 推广到所有卡片比预计难。** 那样 P2a 会顺延。先做通审批卡和问题卡。
- **客户需求会把范围重新吹大。** 先拿到每个客户的第一个场景；客户要的正是冻结模块时，换入一项、换出一项。
- **测试环境就是生产。** 每次部署本地 main，生产上所有租户都会拿到，不只 Rocky 的实验室。所以第一次部署前要确认生产上还有谁在用；每次部署前写好回滚：重新部署 `0866312b`。`0866312b..main` 之间没有数据库迁移，回滚不用动数据库。S0 改了 Telegram webhook 的校验，没重新注册的旧 Telegram bot 部署后会收不到消息，所以 S0 的前两步（只读查存量、重存或重注册）在部署之前做。
- **生产到数据库的往返没单独测。** 现在测试环境就是生产，A2 在 Rocky 的实验室按黄金任务验收，量到的就是生产的往返。达标后仍慢时，再查真实模型首字时间和记忆选择调用。
- **留着的冻结代码会被下一个 agent 接回去。** 冻结清单已写进 AGENTS.md，P3 按计划删除。
- **时间表靠三条线并行。** 任何一片按停止规则停下、或者审查要第二轮，后面都会顺延。每周五按实际进度重排一次，并在每天的汇报里说明。
- **更正。** 上一版风险里写过“人走了、bot 删了，事情谁接手”，前提错了：数字员工本来就不该被删。真实的缺口是三处：
  - 管理员还能删 bot；
