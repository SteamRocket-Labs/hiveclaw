## Authoritative RLS table lists (verified from `app/db_bootstrap.py`)

- **ENABLE+policy (9)** `RLS_TENANT_TABLES`: `agents, users, llm_models, skills, tools, plaza_posts, org_departments, org_members, config_revisions`

- **NOT policied / global (confirmed)**: `tenants` (in `_CORE_APP_TABLES` but NOT in either RLS list), `system_settings`, `tenant_settings`*, `tenant_tool_config`*, `audit_logs`*.
  - *Note: `tenant_settings`/`tenant_tool_config`/`audit_logs` HAVE a `tenant_id` column but are NOT in the RLS lists → no policy today → bare session does NOT fail-closed on them. Flagged in "unsure" for stage-2 scope decision.

Policy USING clause (verified): `current_setting('app.current_tenant_id', true) = 'BYPASS' OR tenant_id::text = current_setting(...) OR tenant_id IS NULL`.
⇒ A bare session (GUC empty) sees ONLY `tenant_id IS NULL` rows on a policied table = fail-closed for tenant-owned rows.

## Notes

- **Note A (chicken-and-egg: agent.tenant_id):** Many call points only receive `agent_id` and must `SELECT agents WHERE id=agent_id` to learn `tenant_id` — but reading `agents` is itself RLS-policied. Two safe patterns: (1) the `agents` policy permits the read only if GUC matches; under a bare session the row is invisible → the lookup returns None and the function fails-soft (degraded, not crash). (2) Preferred: resolve tenant via a short `enter_rls_bypass(reason="resolve agent tenant")` read OR push tenant_id down from the REQUEST/daemon caller so it never has to read `agents` blind. Stage-1 should add a tenant-resolution helper rather than re-implementing per call site.
- **Note B (memory_service.py:792 `_save_session_summary`):** Only `session_id` is in scope, no tenant. ChatSession is stage-2 agent-scoped. Caller chain (`maybe_compress_messages`/session summary) DOES have tenant_id — thread it down, or resolve session→agent→tenant. Don't bypass (this is per-tenant data).
- **Note C (task_executor detached background):** `execute_task` is launched via `asyncio.create_task(execute_task(...))` from `api/tasks.py` — it is REQUEST-initiated but DETACHED (outlives the HTTP request), so the request ContextVar tenant is gone by the time it runs. The first session (line 238) loads `Task` by id with NO tenant available; tenant only known after agent load (line 274). Migration: resolve agent.tenant_id early (one bypass read of Task→agent, or pass tenant_id as a param into `execute_task`), then pin all subsequent sessions. `_log_error` (435) on the failure path also lacks tenant.
- **Note D (capability_reuse partial fail-closed):** Queries use `or_(Skill.tenant_id == tenant_id, Skill.tenant_id.is_(None))`. Under a bare session the `tenant_id == tenant_id` arm returns nothing, but the `IS NULL` arm (global registry skills) still matches → the function returns global skills but SILENTLY LOSES tenant-private ones. This is a **silent-wrong-results** hazard, not a hard crash — worse for debugging. Pin the GUC.
- **Note E (capability_install_service):** `AgentCapabilityInstall` has only `agent_id` (no tenant_id). Today not policied; becomes fail-closed only if stage-2 adds a policy to `agent_capability_installs`. No tenant in scope at call sites (HR creation flow). Decide in stage-2 whether this table gets a join-based policy or a backfilled tenant_id column; until then, no migration strictly required, but flag.
- **Note F (agent_context.py:154):** AgentTrigger queried by agent_id only. Same tenant-resolution gap as Note A. The very next block (310) DOES resolve agent.tenant_id — consider resolving once at function top and pinning the whole function's sessions.
- **Note G (token_tracker):** Deliberately uses an independent session ("to avoid interfering with the caller's transaction"). Has only `agent_id`/`user_id`, no tenant. Writes `agents` + `users` (both ENABLE). Under enforced RLS a bare session sees neither row → token counters silently stop updating (fail-closed = data loss, not crash; `except` swallows it). Must resolve tenant (from agent) and pin, OR pass tenant_id from the invocation. High-value: this is billing/quota state.
- **Note H (quota_guard):** Queries `users` by `user_id` only. Under enforced RLS bare session sees no user row → `check_user_token_quota` returns early (no enforcement) = **fail-OPEN on quota** (quota silently not enforced). Security-relevant: a fail-closed *table read* produces a fail-OPEN *policy decision* here. Must thread tenant (user.tenant_id) and pin, or resolve via bypass. Flag as priority.
- **Note I (audit_logger):** Raw INSERT into `audit_logs` omits `tenant_id` (stays NULL). `audit_logs` is NOT currently policied and even if it were, NULL tenant_id passes the policy. No RLS migration needed today. BUT: NULL-tenant audit rows defeat per-tenant audit isolation — recommend threading tenant_id into the INSERT as a stage-2 data-quality fix (out of pure RLS scope; noted as incidental finding).
- **Note J (activity_logger):** `AgentActivityLog` agent-scoped, no tenant_id, no tenant in scope. Same shape as Note E — depends on stage-2 policy decision for `agent_activity_logs`. Fire-and-forget; failure swallowed → silent activity-log loss under enforced RLS if policied.
- **Note K (tool_config_service.py:154 — only non-`async with` form):** Uses `db = async_session()` with `try/finally: db.close()` guarded by `should_close = db is None`. The caller-provided-`db` branch is already inside a governed session; ONLY the fallback (no db passed) needs the GUC. Migrate the fallback to `tenant_scoped_session(tenant_id)` (note: tenant_id may be None and is resolved from agent inside — same Note A gap if only agent_id given).
- **Note L (skill_distiller):** DAEMON (skill distiller). Queries `chat_sessions` by agent_id only; no tenant. Resolve agent.tenant_id (the distiller already operates per-agent). Pin once.
- **Note M (subagent_evolution):** Both call points query `agents` by id with no tenant — Note A gap. These ride the spawn path (background subagent) AND the apply/reject path (admin REQUEST). `_notify_owner` also INSERTs `notifications` (stage-2). Resolve agent.tenant_id and pin.
- **Note N (retriever._retrieve_episodic):** The parent `MemoryRetriever.retrieve(agent_id, ..., tenant_id)` HAS tenant_id but does not pass it into `_retrieve_episodic`. Cleanest fix: add `tenant_id` param and open `tenant_scoped_session(tenant_id)`. Touches `chat_sessions` (stage-2).
