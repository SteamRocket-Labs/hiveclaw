## 为什么此前陷入循环

1. **深度优先挤压了覆盖。** 当前账本只有 P01 的正常双遍与负向；其恢复失败后，后续修正持续扩展到计账、锁、终态和清理。其余 94 条未执行或只有 finding 证据。原因不只是审查太严，也包括真实共享运行时缺陷和候选越修越大。[账本](../../docs/acceptance/2026-08-30-weekend-rc/04-journey-ledger.md)
2. **有成功条件，没有资源耗尽后的业务出口。** Runbook 第 82 行不设 Goal 总时间/尝试上限，第 194 行要求同路径失败继续调查。它保护了不假完成，却没有阻止同一工作包无限续作。[Runbook](../../docs/acceptance/2026-08-30-weekend-rc/06-runbook-and-release-gates.md)
3. **检查集合容易膨胀。** Finding 链同时列 focused、cross-domain、full、PG、build、i18n、a11y；双审又可能继续扩展相邻路径。应根据实际改动选必要检查，不为每次迭代重跑所有门。
4. **把发现问题、修复问题和最终发布证明混在一起。** 原合同规定任何新应用版本都重跑完整生产双遍。目前反复验证主要发生在 P01，并非已经把 96 条跑过多轮；这一合同若在功能尚未摸清时反复启动，会继续放大重复。先稳定候选再集中发布能减少重复，但不能把旧版本结果迁移成新版本 PASS。
5. **进度记录没有回答产品问题，等待又反复唤醒模型。** 当前状态文件只有 221 行却有 93931 字节，包含大量历史长行。应展示功能结果、剩余阻塞与下一交付，而不是复述报告与哈希。owner 的 15 秒轮询/额度消耗观察需要纠正；“约 60% 周额度由本任务浪费”没有原始归因，不能当作已核实统计。

这些判断不支持“测试都没用”或“安全都可以延后”。例如 MemoryProvider 的类名字符串测试确实存在；它说明某些测试保护实现形状，但不能推出整个测试库无效。真实重复副作用、计费错误、数据丢失和越权仍须处理。

## 推进路径

### 0. 保护现有工作，解除恢复候选对其他功能的绑架

保留暂停的第八轮及全部未提交修改，不直接提交/部署，也不整体删除或重写。先明确本任务候选与 owner 无关改动的边界；后续实现使用独立工作面，避免把半成品带入发布。

功能摸底可在最近有真实证据的生产版本 `17f073bb` 上开展，不依赖未接受的重启候选。隔离已知重启故障及其受影响状态；不能把正常路径可测写成恢复已通过。凡确实共享故障、可能重复效果或损害数据的路径，记录依赖并停止该效果，继续无关功能。

对旧候选只做一次有边界的取舍：为当前失败旅程复用已证实必要部分；不能安全拆分时，整个候选仍未接受，单列一个共享根因工作包。禁止为了“救完旧候选”把全部功能排队等待。

### 1. 先把功能地图展开

先跨 35 组找到真实入口，再补全 96 个变体；每个测试结果直接进入既有账本。覆盖 Agent 开放任务和继续工作、Memory/Growth、个人/公司知识、HR/三角色入口、文件交付、协作/工作流/A2A、Automation/Hook/Skill/MCP/Local Agent、模型与全部 UI。

本阶段遇到失败，保存最小复现和影响范围，继续下一个不依赖它的功能。共同入口完全不可用时才插入必要的小修；单项失败不触发对整个运行时的审计。J4、长期记忆、外部模型和连接生命周期有实际耗时或依赖，单列安排，不从承诺范围删除。

身份、登录、公司选择、连接和合成资产通过现有支持路径复用。仓库可修的缺入口/接线是产品缺陷，不伪装成外部阻塞；真正缺凭据、余额、第三方服务才单列 external readiness。不可用时只验证真实错误和恢复入口，不冒充成功消费。

### 2. 一个实现者、一个验收者，按用户结果迭代

流程：Codex 真实 E2E 发现并明确预期 → zCode 修共享根因并自测 → Codex 审查完整 scoped diff 与受影响调用、核对必要回归 → 批次集成/部署 → Codex 从原入口复验 → 更新结果 → 下一项。

zCode 负责本批次前后端实现；Codex 不边验收边另写一套修正。CC 仅本次讨论，不再成为固定候选门。继续保留 zCode 已确定的 GLM-5.3 默认模型，不因简化协作静默换模型。

每包只写目标旅程、已观察失败、期望行为、允许改动/效果和必要验证。不要求作者制作数百行报告或另建状态系统。相关多个症状可合并为一个真实共享根因包，不能把整个底层都塞进同一个包。

### 3. 修复稳定后，才启动最终发布双遍

摸底和修复期使用既有测试环境及明确批次的生产功能复验；每个生产批次三服务保持同源。代码迭代不反复启动最终 96 条双遍。冻结候选后跑完整相关检查、部署 D，再按原合同集中执行。

最终 D 发生必须修复的缺陷，则修复、生成新 D，并如实重跑原合同要求的完整双遍。不声称按影响面回归等价于原完整双遍；若 owner 另选增量发布验收，必须显式修改合同。故障探针使用合成资产和可恢复效果，回滚与 cleanup 仍在最终范围内。

## 防止再次无限循环的工作规则（owner 已接受）

### 反馈是否能够阻断

- **需要修复：** 冻结要求确实不满足；功能无法完成、结果错误、入口缺失、所需恢复不可用；或可信证据显示越权、泄漏、数据丢失、重复外部效果/计费。危险问题不必为了“有现场复现”去真实制造损害，明确的可达源码证据也可成立。
- **本轮顺手优化：** 同一路径中已见的操作负担、错误说明或重复代码，能用现有实现小改且完成验证，不推迟约定交付。
- **不自动阻断：** 个人架构偏好、抽象层重构、无消费者脚手架、没有合同依据的假想边界；先记录建议，不加入本次验收必过集合。既有已证实缺陷不能改名为优化项来绕过发布。

Codex 每次尽量一次性给出完整反馈，明确对应合同、证据、用户影响和复验方式。复审只检查修正及受影响路径；新的实质缺陷可以提出，但不为了“更严”固定增加新测试、新 reviewer 或新审计面。

开工前冻结的是结果与检查范围，不是不可变的文件数。包外独立问题单列，不能自动延长本包；本包引入的回归仍属于本包。新发现严重危害可以 hold 受影响发布，但必须附具体合同/受保护性质与可达路径的证据，不把“理论上也许”当作无限返修理由。

### 投入上限与改变策略

- 普通缺陷默认一个实现方案、一次集中反馈后的返修；同一根因两次仍不通过，不自动发第三次同类任务。
- 上限触发的是“该工作包需要重新选择策略/明确受阻”，不是“强行通过”。Codex 可以在已授权且不扩大合同的范围内选择更小的方案，说明为何它不同；不得换任务名或拆小票重置原预算。
- 每轮执行建议先给 4 小时工作预算；到点交付实际结果与剩余问题，暂停未获下一轮授权的执行。长模型任务与外部等待单独报告，不伪装成已完成工作。
- 每轮开始前写明目标功能、原有全部未关闭问题、本轮结束时间与可用消耗预算。已批准的额度不能因拆包、改任务名、重启 agent 或创建新 Goal 自动刷新；没有本任务可核实 token 计数时，以时间和调用/重试预算约束，并披露 token 不可用。
- 修复会改变产品语义、需要重要风险接受或额外时间/费用时，给 owner 一个明确选择；不为可从源码判断的日常事项反复提问。
- 最终发布循环同样要有约定的候选/投入预算；耗尽时交付“未达到发布条件”及具体原因，不能无限自动生成 D3、D4。

长期 North Star 是方向，不作为这一轮无限扩展的清单。本次 RC 完成仍以冻结要求与真实证据判断；某轮预算耗尽只是该轮结束，产品目标保留未完成。新想法、新审计建议和非必要优化不会在末尾自动追加为新的完成条件，也不会在达标后自动开始下一阶段底层治理。

具体分钟数与批次规模是初始工作预算，不是经验测出的工期保证，也不裁决产品质量。其原则需要替代旧 Runbook 的无 Goal-wide 上限；最终质量门与分母不因此降低。

### 测试、等待与可见进度

测试优先复用既有行为检查。每个新故障留能捕获真实回归的最小保护，多个同根因场景可参数化复用；不按“每次改动”新增一套。检查应能回答：保护哪个真实行为、什么坏实现会让它失败、现有测试是否已经覆盖、为什么现在必须运行。普通迭代跑受影响检查；完整相关 suite 在候选集成/发布节点跑。不要现在另开全仓测试大清洗或覆盖率工程；发现重复或仅锁定类名的检查时，只在触及路径中核对消费者后精简。测试环境故障与产品失败分开记录，不能靠反复 rerun 抹掉原因不明的 flaky failure。

等待优先完成通知或现有 CLI 挂起等待；没有通知时退避读取小状态，不让大模型每 15 秒检查一次，不反复读取整份报告，也不叠加多个 heartbeat。等待超时不是任务失败；仍在运行的原任务不得重复提交。限额/明确失败只在有新条件时重试。

每个约定批次给一个短业务卡：本轮实际测了什么、修复后多通过了什么、还剩哪些 blocker、下一批交付。附实际可获得的代理调用/测试/部署次数、耗时与 token；无法取得本任务 token 时写不可用，不把账户额度变化直接归因给它。状态文件正文只放当前结论，原始证据保留引用。

## 第一个低成本检验与置信度

建议 owner 接受后先运行 **2 小时试批次**，不是立即恢复无期限 RC Goal。前置确认现有合法身份、选定公司和必要连接可以进入目标路径；不提前建设通用 fixture 平台。从不同业务域选择可独立进入的真实路径，证明工作能从 P01 扩展出去；遇到缺陷给出用户影响及最小修复包，不展开底层。

试批次到点交付实际通过/失败/阻塞证据、每类耗时、重复劳动与下一批估算。如果仍只有恢复候选的审查记录、没有跨域实际结果，就认定当前办法未被证明有效，停止照旧续作。如果共同身份或入口挡住多条，应先交付一个最小可复用入口修复包，而不是继续碰同一个前置失败。外部依赖阻塞应给可回读原因；不能用“已分类”伪装执行过。试批次只验证推进方式，绝不代替 96 条全量测试。

随后依据观测估计首轮全量功能测试工期，并分开列模型长任务、修复和最终双遍时间。当前没有足够实测吞吐，不能再给一个无依据的“一周全部完成”承诺。

“95% 以上把握”应通过关键环节有明确处理与小批次实证来争取；现在不能诚实宣称 95% 的按期完成概率，也不能把 Evidence Coverage 95 分或两名模型同意当作概率。最关键的未决因素是其余功能真实缺陷数量、旧候选可拆性和外部能力可用性。
