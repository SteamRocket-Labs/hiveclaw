# CCPlus 前端产品体验契约

## 1. 定位

前端不是后端对象、runtime 事件和治理字段的可视化调试器。它是 Agent 能力被用户理解、介入、恢复和消费的产品平面，也是七原子中 **Consumption** 的主要事实面。

Hive 的前端目标不是复刻某一版 Codex Desktop 的像素、三栏布局或组件树，而是吸收它更稳定的产品哲学：以任务和结果为中心、状态连续、渐进披露、操作就近、交付优先、技术证据可追溯但不打扰普通用户。

本契约服从两个北极星：

1. 单 Agent 智能、自进化与完整 CC / FreeCode 生命周期先成立；
2. 企业控制中台让公司可以安全地运营这些 Agent。

前端不得通过隐藏真实失败、伪造完成状态或删除能力来换取“简洁”。简洁来自信息层级、受众分层和唯一事实投影，而不是信息丢失。

## 2. 产品对象与信息优先级

普通用户面对的首要对象是 **一项要完成的工作**，不是 Agent、RuntimeTask、Tool Call、Span 或数据库实体。默认信息优先级固定为：

1. **结果与交付物**：完成了什么，可以打开、下载、继续修改或分享什么；
2. **需要用户做什么**：问题、审批、选择、补充材料或恢复动作；
3. **当前进度**：正在解决什么、有何可信里程碑、由谁负责下一步；
4. **关键决定与变化**：计划、重要发现、范围变化和影响结果的取舍；
5. **失败与恢复**：发生了什么、保留了什么、用户可以重试、继续、修改方向还是联系管理员；
6. **技术证据**：原始事件、trace、schema、ID、provider payload、token、tool arguments 和 forensic metadata。

第 6 层默认只属于 Operator / Audit Surface。它可以被授权用户主动展开，但不能占据普通会话和首页的主视觉。

## 3. 受众分层

### 3.1 普通用户

普通用户需要看到：目标、可理解的进度、Agent 的必要说明、待办动作、结果、交付物、引用、失败影响和可恢复操作。

普通用户默认不看：内部 schema、UUID、run/turn/correlation ID、原始 tool 名称与参数、provider 错误、token 细账、heartbeat noop、RLS/ACL 实现细节、raw JSON、无消费价值的后台队列事件。

### 3.2 Owner / Manager

Owner 或 Manager 需要在独立的管理视图中看到：Agent 资产、工作分配、能力与知识范围、预算、审批队列、风险、使用情况、失败摘要和可操作的治理状态。

管理视图也不等于调试视图。Manager 看业务影响和治理动作，Operator 才看实现证据。

### 3.3 Operator / Auditor

Operator / Auditor 可以看到：完整 typed state、事件顺序、trace/span、调用参数、事实源链接、错误分类、恢复记录、权限裁决和审计证据。

进入该视图必须基于可信 principal、能力与显式用户动作。不要因为用户是 Agent owner 就自动把普通会话切换为工程控制台。

## 4. 核心表面合同

### 4.1 首页

首页回答四个问题：

1. 哪些工作需要我处理；
2. 哪些工作正在推进；
3. 最近产生了哪些结果或交付物；
4. 我从哪里开始一项新工作。

首页不应直接显示 raw tool activity、provider/HTTP 错误分类、token 细账、heartbeat 或所有 Agent 的完整角色文本。成本与故障运营进入管理面；普通活动必须被投影成用户语言，并且能够回到对应任务或结果。

### 4.2 导航与左侧栏

左侧栏只承担稳定导航与最近工作切换。不要同时堆叠全局模块、所有 Agent、每个 Agent 的全部 Session、筛选器、管理动作和删除按钮。

默认结构应围绕“最近工作 / 项目或员工 / 已固定入口”建立。搜索、归档、管理和破坏性动作按需出现。层级深度、数量和当前上下文必须在不同屏宽下可读。

### 4.3 Agent 概览

Agent 概览首先表达：这个数字员工能帮助用户做什么、当前承担什么工作、最近交付了什么、何时需要关注。Capabilities、Memory、Knowledge、A2A、Workflow、Permissions 等系统概念可以存在，但应进入清晰的二级产品入口或管理入口，而不是把一个 Agent 页面变成全部内部模块的平铺目录。

Runtime protection、heartbeat、provider、token、底层状态机和审计字段不属于普通概览的默认内容。

### 4.4 Session / Thread

Session 的中心是人与 Agent 围绕一项工作持续协作。默认应显示：

- 用户请求与 Agent 有意义的表达；
- 简洁但真实的进展；
- 就近出现的问题、审批和恢复操作；
- 关键计划、决定、结果与引用；
- 当前会话的交付物。

Tool call、tool result、runtime event、subagent message 和 workflow event 先被投影为用户可理解的活动；原始证据通过渐进披露进入 Operator View。不得用平台固定 prose 替换模型最终表达。

### 4.5 右侧上下文面板

右侧面板不是常驻的 runtime console。它只在对当前任务有消费价值时出现，优先顺序为：

1. 当前交付物；
2. 当前需要用户处理的事项；
3. 仍在运行的有意义进度；
4. 可选的团队、工作流和历史证据。

没有内容的分区隐藏，不用四个“0”证明系统存在。已结束会话默认收起运行细节。窄屏时面板变为抽屉或任务内入口，而不是挤压正文。

### 4.6 Workspace 与 Artifact

Workspace 必须区分：

- 当前会话确认交付的文件；
- 用户作为输入提供或显式引用的文件；
- Agent 长期工作区中的历史文件；
- 来源不明、待归因或被拒绝交付的文件。

聊天正文、右侧交付物、Workspace 和下载能力必须消费同一 artifact receipt / provenance truth。正文说“已交付”而侧栏为 0，或文件存在但不可下载，都是发布阻断级 Consumption 断点。

### 4.7 多智能体与 Workflow

Sub-agent、Agent Team、A2A 和 Dynamic Workflow 的内部拓扑不应成为普通用户的理解负担。默认只表达：为什么需要协作、谁在负责哪一部分、当前整体状态、是否需要用户介入、何时回到主 Agent、最终如何合并结果。

只有当成员差异、并行进度或冲突会影响用户决策时才展开成员级细节。内部 Agent ID、消息总线、runtime task 和叶子调用留在 Operator View。

### 4.8 企业控制中台

公司治理、AI 资产、权限、预算、审计和知识管理必须有独立的信息架构。管理面的目标是可理解、可操作、可追责，不是把数据库表和策略 JSON 做成页面。

普通 Agent 使用面与公司控制面可以互相链接，但不能在一个默认页面混合其受众、术语和操作风险。

## 5. 状态表达语法

所有用户表面使用同一套语义状态投影。具体内部状态可以更多，但用户至少能稳定理解：

- 尚未开始 / 已排队；
- 正在工作；
- 等待用户；
- 已暂停，可继续；
- 已完成；
- 失败但可恢复；
- 已取消。

每个非终态或异常状态必须回答：正在发生什么、下一步由谁负责、已有结果是否保留、用户可以执行什么动作。`idle`、`noop`、`runtime_task missing`、`provider_timeout` 等内部状态不能未经翻译成为主文案。

刷新、重连、恢复、跨设备、历史回放和 fork 后，同一机械事实必须投影为同一用户状态；不允许 transient UI 自己发明第二套终态。

## 6. 视觉与交互原则

1. **内容优先**：文档与对话是主角，容器服务于层级；避免卡片套卡片和无意义边框。
2. **克制但精致**：少量字号、间距、圆角和状态色；颜色表达语义，不装饰噪声。
3. **单一主动作**：每个视图有清晰的下一步；次要和危险动作渐进披露。
4. **连续反馈**：hover、pressed、focus、loading、streaming、waiting、success、failure 和 disabled 都有一致状态。
5. **空状态节制**：无内容的面板默认消失；需要教育时才展示短而可操作的空状态。
6. **自适应而非固定三栏**：布局由任务和屏宽决定；侧栏、上下文面板都可折叠或转为抽屉。
7. **无障碍是质量基线**：键盘、focus order、screen reader 名称、颜色对比、reduce motion 和触屏目标必须进入验收。
8. **语言完整性**：同一 locale 不混杂未翻译的英文；占位符、计数、日期、时区和复数规则必须正确。

## 7. 七原子在前端的解释

| 原子 | 前端必须回答 |
|---|---|
| Input | 用户从哪里发起，输入是否明确、可编辑、可恢复和可关联到当前工作 |
| Authority | 当前用户为什么能看到或操作该信息；普通、Manager、Operator 是否正确分层 |
| Execution | 点击后进入哪条唯一受治理执行路径；是否存在 UI 旁路或重复提交 |
| Evidence | 屏幕状态来自哪个机械事实源；不同组件是否使用同一 receipt/read model |
| Recovery | 断线、失败、取消、拒绝、过期和刷新后用户如何继续，已有结果是否保留 |
| Consumption | 结果、交付物、引用、进度和治理决定是否真的能被用户找到和使用 |
| Acceptance | 真实浏览器旅程、角色分层、视觉、无障碍、故障和状态一致性是否被验证 |

## 8. 验收合同

### 8.1 必须使用真实旅程

至少覆盖：新建工作、长任务、问题或审批、可恢复失败、交付文件、历史恢复、Branch/Rewind、Sub-agent/Team、Workflow、权限拒绝和普通完成。场景来自当前产品和真实风险，不把这张清单机械转换成固定脚本。

### 8.2 必须做跨表面真值对账

对每条代表性 trace，把 backend truth、transcript、会话正文、状态头、右侧栏、Workspace、通知和管理面逐项对账。状态、数量、归属、可下载性、失败原因和下一步不能互相矛盾。

### 8.3 必须分角色取证

普通用户、Manager/Owner、Operator/Auditor 分别取证。禁止只用超级管理员截图证明普通用户体验，也禁止只写 `audience` 判断而不验证生产 principal 与 UI 入口。

### 8.4 视觉与交互证据

关键状态保存版本匹配的截图或录像；覆盖典型桌面宽度、窄屏、light/dark、键盘路径、focus、loading、empty、error、waiting 和 completed。截图回归只能补充，不能替代真实任务成功和语义一致性。

### 8.5 判定方式

- schema、权限、receipt、artifact 数量、状态映射、可下载性、重复效果和路由使用机械断言；
- 信息层级、文案可理解性、视觉质量、认知负担和 Codex 参考差距使用事先校准的人类或 model rubric；
- 不用自然语言关键词扫描替代受众与结构化来源判断；用户或 Agent 正文恰好包含技术词不应被误判为 UI 泄漏；
- 仅 mock 的 Storybook、synthetic fixture 或截图测试不能证明生产消费闭环。

### 8.6 发布硬阻断

以下任一项成立时，用户体验相关声明不得 GO：

- 关键结果或交付物在任一主消费面丢失或互相矛盾；
- 用户不知道下一步由谁负责，或失败后没有真实恢复动作；
- 普通用户默认暴露越权数据或 Operator 级原始证据；
- UI 显示完成但事实源未完成，或显示 0/空但存在当前有效结果；
- 普通核心旅程无法通过键盘或关键内容不可访问；
- 只完成视觉换皮，功能语义、状态或恢复仍断裂。

## 9. 与 Codex 的关系

Codex 的价值不是某个静态布局，而是把项目/任务组织、当前线程、进度、审批、变更和结果放在连续协作关系中；同时让 sandbox、worktree、typed items 和技术证据支撑产品，而不是统治产品。Hive 应保留这种克制和连续性，并把它推广到非代码数字员工、知识工作交付物、Hive Native 与企业治理。
