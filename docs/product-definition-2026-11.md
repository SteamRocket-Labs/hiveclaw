# 产品定义（2026-11）

owner 2026-11-03 批准的重启计划里，产品定义、问题的共性、验收和黄金任务都迁到本文件。`AGENTS.md` 引用的就是它。

## 一句话

团队里每个人都能用的 Claude Code 级助手。

- 主路径只有一条：**对话 → 干活 → 拿结果**。一段代码如果不在这条路上，也不属于下面的六条治理底线，本轮就不再投入。
- 入口：Web 对话是主入口。在 IM 里也能派活，支持飞书、钉钉、企微、Slack、Telegram，和 Web 共用同一个内核。
- 三个“一次就够”：一句话就能建 bot；应用连一次，全员复用；拿到的结果可以接着改。
- 部署：云上和私有化都要做。这是两种不同的需求，分开交付。
- 第一批用户：我们自己的团队，每天用；另外有 3–4 个客户在等着落地。
- 差异化：CC 级的能力，Grok 式的同事体验，公司的东西归公司、管得住。管理体系是我们和 Grok 的区别，它放在管理员那一侧；成员只在对外或不可逆的那一刻碰到它。“每一步都证明一遍”的那类机制仍然冻结（owner 11-04 定，见计划正本第 1.3 节）。这一条取代 10-04 的 D2“中立的组织级数字员工治理”。

## 治理底线（只有这六条）

1. 租户隔离
2. 登录 / SSO
3. 个人数据默认私有
4. 对外可见或不可逆的动作要先批准，批完在原处接着跑
5. 凭据统一托管
6. 审计日志和预算上限

## 本轮冻结

以下各项不再投入，之后删除：

- 持久电脑和私有浏览器的新机制
- 远程 A2A
- 组织身份切换
- 原件生命周期
- 每次读取都要做的收据和来源校验
- 处处对账
- 第三方 Agent 入编的新增部分（现有的本地桥保持原样）

客户明确要其中某一项时，用“换掉一项”的方式放进来，不追加。

## 问题的共性和改的原则

慢、状态不准、界面全是内部词、员工动不动就停、IM 出错不报，这几件事是同一个问题的不同表现：**“证明每一步都没错”被放进了用户等待的路上，而且每一层各证明一遍；真正会出错的对外边界，反而没人验证。**

| 表现 | 用户看到的 |
|---|---|
| 每一层各自重新确认身份、权限、来源，并同步写证据 | 慢。每轮对话、每次工具调用、每条 IM 消息都要多等这一段 |
| 证明过程的中间状态被当成了用户状态 | 状态不准；界面和报错里出现回执、来源绑定、主体、租约、对账这类词 |
| 证明不过就把整条路停下来 | 用户觉得“严”：整轮被终止，自己的文件被隔离，补充的消息丢失 |
| 力气都花在内部证明上，对外边界没人验证 | IM 发送失败却记成成功、入站请求不验签、回调地址指向外部域名、私有化没在干净机器上装过 |

改的时候按这几条原则：

- 一轮开始时确认一次身份和权限，往下传，各层不再各自确认。
- 只在对外可见或不可逆的动作发生那一刻检查。
- 内部状态不给用户看。
- 检查不通过，只拿掉那一件事，其余照常进行。
- 对外边界用真实渠道和真实安装来验证。

## 验收：怎样才算“拿得出手”

| 编号 | 能看到的结果 | 怎么查 |
|---|---|---|
| P1 | 点发送后 300 ms 内，能看到自己的消息和“思考中”；模型本身以外，平台开销小于 1 秒 | 6 个黄金任务逐个计时，在预发环境各跑 10 次取中位数 |
| P2 | 状态只有五种：运行中、等你决定、完成、失败、已停止，任何时刻都和真实运行一致 | 五种状态各截一张图，对照后端的运行记录 |
| P3 | 默认界面只剩对话、输入框、附件、当前模型、停止；界面文字里不出现内部词 | 截图，并在 i18n 文本里检索这些词 |
| P4 | 6 个黄金任务在 Web 和飞书上各跑通一遍 | 录屏，每项附运行记录 |
| P5 | 自己团队连续用 5 个工作日，没有出现“卡住了只能找管理员”的情况 | 每天收集问题清单，清零才算通过 |

测试全部通过是必要条件，但不能代替上面这些证据。

## 6 个黄金任务

1. 说 hello。
2. 读一个文件，写一份报告，报告能下载。
3. 一句话建一个 bot，并给它派第一个任务。
4. 连一次飞书文档或 MCP 之后，另一个 bot 直接就能用。
5. 一个需要审批的对外动作，批准后在原处接着跑。
6. 人改过成果之后，让 bot 在改过的版本上接着改。
